# Шпаргалка к защите (Budget Tracker)

Защита 15-20 минут, спросить могут любого из команды по любой части проекта. Этот файл помогает за час понять проект целиком. Читай его вместе с кодом, открыв файлы из списка.

## 1. Питч за 30 секунд

«Budget Tracker это веб-приложение для учёта доходов и расходов на Blazor WebAssembly. Оно работает без регистрации и без сервера: данные хранятся в браузере. Логика вынесена в отдельный слой Domain и написана в функциональном стиле: неизменяемые records, чистые функции, ошибки как значения через `Result`. Это позволило покрыть логику unit-тестами. Из дополнительных возможностей: лимиты по категориям с предупреждением на 80%, график за 6 месяцев, светлая и тёмная тема.»

## 2. Как данные проходят через приложение (главное, что нужно уметь рассказать)

1. Пользователь заполняет `TransactionForm.razor` и нажимает «Add».
2. Форма разбирает текст в число и дату (`InputParser`), собирает `TransactionDraft` и вызывает функцию `Save`, которую ей передала страница.
3. Страница передаёт вызов в `AppState.SaveTransactionAsync`.
4. `AppState` вызывает `TransactionValidator.Validate`. Это чистая функция, она возвращает `Result<Transaction>`: `Ok` или `Fail` со списком ошибок.
5. Если `Ok`: создаётся **новый** снимок данных `_data with { Transactions = ... }`, он сериализуется в JSON (`DataSerializer`) и сохраняется через `IStorage` в LocalStorage.
6. `AppState` вызывает событие `OnChange`. Все компоненты, унаследованные от `AppStateComponent`, вызывают `StateHasChanged` и перерисовываются.
7. Если `Fail`: форма показывает список ошибок, данные не меняются.

## 4. Вопросы, которые часто задают, и короткие ответы

**Почему Blazor WebAssembly, а не Blazor Server?**
Не нужен сервер: приложение это статические файлы, их можно выложить на GitHub Pages. Минус: первая загрузка тяжелее (скачивается .NET в WebAssembly), поэтому включена обрезка (trimming).

**Где здесь функциональное программирование?**
Неизменяемые `record`; чистые функции в `Domain/Logic`; конвейеры LINQ вместо циклов с накоплением; `Result<T>` вместо исключений; pattern matching через `switch`; побочные эффекты (LocalStorage, переключение темы) только на краях: `AppState`, `LocalStorageService`, `BrowserService`.

**Зачем `Result`, если есть исключения?**
Неверный ввод это ожидаемая ситуация, а не авария. `Result` делает возможность ошибки частью типа: компилятор и `switch` заставляют обработать оба случая. Исключения остаются для настоящих сбоев (например, хранилище недоступно): они ловятся в `AppState`.

**Как устроено управление состоянием?**
Паттерн state container: один сервис `AppState` хранит неизменяемый снимок `AppData`. Любое изменение создаёт новый снимок, сохраняет его и вызывает `OnChange`. Компоненты подписываются на событие в базовом классе и отписываются в `Dispose`. Настройки (валюта) передаются вниз через `CascadingValue`.

**Что будет, если LocalStorage повреждён или переполнен?**
Повреждён: `DataSerializer` возвращает `Fail`, приложение стартует пустым, копия повреждённых данных сохраняется под отдельным ключом, пользователь видит предупреждение. Переполнен или отключён: данные остаются в памяти, приложение работает, пользователь видит красное сообщение, что изменения пропадут после закрытия вкладки.

**Почему Domain это отдельный проект?**
Он не зависит от Blazor и браузера, поэтому тесты запускаются быстро и без браузера, а хранилище или UI можно заменить, не трогая логику. Это основа масштабируемости.

**Как устроена адаптивность?**
Свой CSS на flexbox и grid. Брейкпоинт 900 px: боковое меню превращается в нижнюю панель. Брейкпоинт 700 px: колонки становятся одной колонкой, строки таблицы превращаются в карточки (через `data-label`).

**Что вы тестировали и как?**
xUnit: вся логика Domain (валидация, отчёты, лимиты, JSON, фильтр) и `AppState` с подменённым хранилищем `FakeStorage`, включая сбои чтения и записи. bUnit: компоненты. Ручное тестирование: таблица в `docs/QA.md` (браузеры, устройства, ширины экрана).

**Что бы вы улучшили?**
Регулярные платежи, импорт и экспорт CSV, офлайн-режим (PWA), синхронизация между устройствами через API (хранилище уже за интерфейсом `IStorage`), несколько валют с курсами, бюджеты по периодам, e2e-тесты Playwright, уведомления о лимитах.

## 5. Сценарий демо (5 минут)

1. Открыть сайт на GitHub Pages. Показать пустой Dashboard.
2. Добавить доход и три расхода в разные категории. Показать, как обновился Dashboard.
3. Ввести неверную сумму (`abc`, потом `0`): показать сообщения об ошибке.
4. Лимиты: поставить лимит на Food, потратить больше 80%, затем больше 100%. Показать предупреждения.
5. Reports: графики по категориям и график за 6 месяцев.
6. Settings: переключить тему и валюту. Показать, что всё сохраняется после перезагрузки.
7. Сузить окно до 360 px (или показать телефон): нижнее меню, карточки вместо таблицы.
8. Показать зелёный прогон `dotnet test` и вкладку Actions.
